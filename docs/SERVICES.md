# Day 7 services

Run `pnpm test:services` for real Postgres and Anvil integration tests without Docker. Install Node 22+, pnpm 10.33.0 and Foundry first. `pnpm install` allows the embedded Postgres native setup script through the workspace allowlist.

For long-running services, set `DATABASE_URL`, `RPC_URL`, `DEPLOYMENT_FILE`, `ATTESTER_KEY`, `KEEPER_KEY` and `API_TOKEN` in `.env`. The API token must have at least 24 characters. Use separate attester and keeper accounts across deployed processes to avoid nonce contention. Both need testnet gas; only the attester must be registered with the registry. `ROLE` is `api`, `keeper`, `arena-worker` or `all`. Run `pnpm services`. Migrations run under a database lock before each role starts. `ROLE=migrate node apps/api/dist/main.js` runs migrations alone after building.

`docker compose up --build` runs Postgres 16 and all roles. Docker must be running and the configured RPC must be reachable inside the container. The image does not depend on git submodules being present: the Dockerfile fetches forge-std and OpenZeppelin at the commits the repository pins unless the copied checkout is readable and already at those commits. This covers Railway's source snapshot, which has no submodules, and local builds, where `.dockerignore` drops the git metadata. If you update a submodule, update `FORGE_STD_COMMIT` or `OPENZEPPELIN_COMMIT` in the Dockerfile to match `git ls-tree HEAD contracts/evm/lib/forge-std contracts/evm/lib/openzeppelin-contracts`.

## Railway

The Railway project (Postgres, its volume, and the `api`, `keeper`, `arena-worker` and `sentinel` services) is defined in `.railway/railway.ts`: the Dockerfile build, start command, health check and non-secret variables. Restart on failure (10 retries) and sleeping off are Railway's defaults, so the file leaves them out; spelling them out makes every plan report a false change. Signing keys and the API token are secrets kept on Railway; the file marks them `preserve()` so their values never enter the repository. The public domain is generated by Railway and is not in the file.

To change the setup, edit that file, then run the following from the repository root with the Railway CLI linked to the project:

```bash
railway config plan
```

`plan` changes nothing and lists what would change. Review it, especially anything it would destroy: a resource removed from the file is deleted on apply. Then run `railway config apply`. There is no automatic apply on merge while CI is paused, so apply after the change is merged to `main`.

Setting a secret (for example a new `KEEPER_KEY`) is done on Railway, not in the file:

```bash
grep '^KEEPER_KEY=' .env | cut -d= -f2- | tr -d '\n' | railway variables --service keeper --set-from-stdin KEEPER_KEY
```

### Solana claims

The `keeper` service also files Solana claims (`SolanaKeeper`, ADR-011) once two variables are set on it. Claims are permissionless, so its key only pays fees; a fraction of a devnet SOL lasts a long time.

1. Create a key. It stays on this Mac and on Railway, never in the repository:

```bash
solana-keygen new --no-bip39-passphrase -o ~/.config/bonded/solana-keeper.json
```

2. Fund its address (`solana-keygen pubkey ~/.config/bonded/solana-keeper.json`) with 0.1 devnet SOL at faucet.solana.com.
3. Set both variables:

```bash
railway variables --service keeper --set "SOLANA_RPC_URL=https://api.devnet.solana.com"
```

```bash
tr -d '\n' < ~/.config/bonded/solana-keeper.json | railway variables --service keeper --set-from-stdin SOLANA_KEEPER_KEY
```

Without them, the keeper runs EVM only, as before.

### Sentinel

The `sentinel` service is different: it builds `services/sentinel/Dockerfile` (Laya's Python server, see `services/sentinel/README.md`), listens only on the private network at `http://sentinel.railway.internal:8000`, and has a 4 GB memory cap and 2 vCPUs. It pins the model with `SENTINEL_MODEL_REVISION`; change that only after the held-out evaluation (`docs/SENTINEL.md`). Its two secrets are set once:

- `HF_TOKEN`: a Hugging Face **read** token (huggingface.co → Settings → Access Tokens → type Read), so it can download the private model. Not the write token used on Kaggle.
- `LAYA_API_KEY`: the bearer key callers send. Generate one; callers read the same value.

The first command waits silently: paste the read token and press Enter. It isn't echoed or stored in shell history.

```bash
read -rs HF && printf %s "$HF" | railway variables --service sentinel --set-from-stdin HF_TOKEN; unset HF
```

```bash
openssl rand -hex 32 | tr -d '\n' | railway variables --service sentinel --set-from-stdin LAYA_API_KEY
```

The first start downloads the model (about 1.7 GB), so the deploy takes a few minutes before its health check passes.

Do not accept Railway's offer to create one service per pnpm package (`@bonded/arena`, `@bonded/api` and so on). The packages are not separate services; all three services build the root `Dockerfile` and differ only in `ROLE`.

Railway injects `PORT`; the API reads it. Every service runs migrations under a database lock before starting, so start order does not matter.

The hosted services load `config/agents.46630.json` (agent 2, the scripted hardened adapter from Gate 1; its mandate hash matches the one attested on chain). Provision agents through `AGENTS_FILE`, a JSON array of `{ "kind": "hardened", "mandate": <full EVM mandate>, "codeHash": "0x…" }` records. `kind` is `hardened`, `vulnerable` or `partial` (the demo's Agent A: the hardened guard with one gap, see docs/PLAN.md Day 14), selecting the scripted demo adapter. Agent IDs must already exist on the configured chain; the mandate's chain and agent ID must match. Keep this file server-owned. On startup, a supplied file is the complete set of operator agents for that chain (agents registered by their owners through `/self/agents` are not affected): removed operator agents are disabled and their queued/running jobs are failed (active workers stop at their next lease check), while historical reports and attestations remain readable. An empty array disables the entire chain's configured set; omitting `AGENTS_FILE` leaves it unchanged. Already-broadcast transactions cannot be cancelled. Arbitrary submitted agent code and LLM configurations are outside this initial worker interface.

POST endpoints require `Authorization: Bearer <API_TOKEN>`, except: a bounty reveal (the spec's hash against the chain authenticates it); the self-serve routes (signed by the agent's owner in their wallet; the exact message is `selfServeMessage` in `@bonded/shared`); and `/quotes`, which without the token caps cover at 20,000 tUSDG and is rate-limited. GET endpoints are public.

Browsers can call the API only from origins listed in `WEB_ORIGINS` (comma-separated, for example `http://localhost:5173,https://bonded.vercel.app`). An https entry may have one `*` for part of a single host label, so `https://bonded-*-ddboy19912s-projects.vercel.app` covers the web app's Vercel preview deployments. Other origins get no CORS headers. CORS only decides which pages can read responses in a browser: nothing on the API relies on it for access, since writes need the operator token or a wallet signature. The hosted `api` service sets it in `.railway/railway.ts`.

| Request | Body / result |
|---|---|
| `GET /health` | Database availability and configured chain ID |
| `POST /arena/runs` | `{ "agentId": "1" }` → `runId` |
| `GET /arena/runs/:id` | Status, report and retry error |
| `GET /arena/runs/:id/report` | Report or 202 while pending |
| `GET /agents/:id/score` | Latest worker-posted signed attestation and transaction hash |
| `POST /quotes` | `{ "agentId": "1", "vault": "0x…", "coverAmount": "20000000000" }` → signed quote |
| `GET /episodes?page=&limit=&through=&runId=&agentId=&attack=&outcome=&class=&source=&since=` | Arena episodes, newest first, as numbered pages (25 by default, at most 100) of a snapshot: the first request returns `through`, the newest event id, and later pages pass it back, so pages keep their rows while episodes arrive. Filters run in the database: `outcome` (`held`, `breach`, `control`), `class`, `attack` (one attack's id), `source` (`held-out` or `library`), `since` (`1h`, `24h`, `7d`), `runId`, `agentId`. Returns `{ items, page, pages, total, through, counts }`; `counts` are by outcome with every filter but the outcome |
| `GET /events?runId=<uuid>&after=<id>` | SSE episode feed after event `after` (the web passes the snapshot's `through`); optional run filter, `Last-Event-ID` replay |
| `POST /bounties/:id/reveal` | The attack's YAML as the body (no token) → 202 `{ created, status }`; see [BOUNTIES.md](BOUNTIES.md) |
| `GET /bounties?page=&limit=&status=&class=&hunter=&submission=&sort=` | Submissions with status, reward, reason and transaction, without payloads, as numbered pages (`{ items, page, pages, total }`); newest first, or `sort=reward` |
| `GET /library` | What ratings run, as counts only: published seeds, accepted bounties, and active held-out attacks with the earliest retirement date |
| `GET /library/attacks?page=&limit=&class=&surface=&severity=&sort=` | The published attacks (no planted text), numbered pages, each with its record in the Arena episodes on record: episodes, breaches, runs, last run. `sort` is `class` (default), `breaches` or `rate`. `statsSince` is when the oldest episode on record ran. Held-out and bounty attacks are never listed |
| `GET /library/attacks/:id` | One published attack in full, planted text included, with its record; an unpublished id is 404 |
| `POST /library/held-out` | Upload held-out attacks (operator token): `{ specs: [yaml, ...], retireAfter }`, up to 10 a request; ids must look like `A6-held-out-1a2b3c4d`. See ADR-007, decision 3 |
| `GET /self/agents/:id` | Whether an agent is registered for self-serve ratings, its design, and when it can be rated next |
| `POST /self/agents` | Register an agent for ratings (no token): `{ agentId, vault, kind, mandate, timestamp, signature }`, signed by the agent's owner, who must also be the vault's guardian; the mandate must hash to the vault's on-chain mandate hash |
| `POST /self/agents/:id/rate` | Queue a rating (no token): `{ timestamp, signature }`, signed by the agent's owner; one per agent an hour, 40 a day across self-serve agents |

Amounts are integer strings in base-asset units. Quotes use the registry score and one block's pool exposure, bond and caps, then simulate `buyCover` as the guardian. Quotes do not reserve capacity: chain state can change before purchase, and the contract checks again. Missing or invalid chain state currently returns a generic 503; underwriting cap failures return 409.

The report endpoint returns the exact JSON bytes hashed by the attestation; a text column preserves them alongside the queryable JSONB report. Migration 2 adds this column without fabricating original bytes for older rows.

The worker rates on a local fork, never against the live RPC. It awaits every episode write, saves the report and signature, then posts the attestation to the configured registry. Jobs get at most three attempts, including expired leases from process crashes, and then remain `failed` for inspection. The next claim reaps exhausted leases, updates rating status and emits a failure event. The keeper role deletes `events` rows older than `EVENTS_RETENTION_DAYS` (default 30) once an hour, in batches of 10,000, oldest first. Ratings, reports, attestations and claims are not touched. An SSE client resuming from a deleted `Last-Event-ID` continues from the oldest kept event. SSE admits at most five simultaneous subscribers per API instance, returning 503 beyond the limit. Each stream reuses its reserved listener for replay queries, leaving the rest of the 15-connection pool for ordinary operations. Connection waits and stream queries time out after five seconds. Shutdown stops admission, aborts active streams (including slow readers), waits for listener cleanup, and then closes Postgres.

The keeper scans up to 500 blocks per tick, with five confirmations by default (`KEEPER_CONFIRMATIONS=0` only for local tests). It accrues active policies once an hour (`KEEPER_ACCRUE_MS`, default 3,600,000). Each accrual is one transaction per active policy, so this sets most of the keeper's gas use; claims, cancellations and new cover accrue on chain when they happen anyway. Breaches stay pending after RPC or liquidity failures. No-match breaches become `ignored` with a reason once the policy cursor has passed the breach timestamp; until then they remain pending so a not-yet-indexed policy at the same timestamp is not missed. Claims are checked against historical coverage windows and simulated after accrual. A deep reorg triggers an error and stops scanning until an operator reconciles the database. Operations alerts (including a low keeper balance) go to Telegram; see "Alerts" below.

## Monitoring

What watches the hosted services today:

- **Health check.** Railway calls `GET /health` on `api` during each deploy and keeps the previous deployment serving if the new one fails it. The endpoint reports database availability and the configured chain ID.
- **Restarts.** All three services restart on failure, up to 10 times. A service that keeps crashing stops and shows as crashed in the dashboard; Railway emails the workspace owner about failed deploys and crashes.
- **Spending.** The workspace has a $10 soft limit (email) and a $25 hard limit (Railway stops the services). Normal use is about $3 a month: roughly 0.2 GB of memory and 0.03 vCPU across the four services. Check with `railway usage`.
- **Keeper progress.** `keeper_cursors.block_number` should stay within a few blocks of the chain head. `handled_events` rows with `status='pending'` and a non-empty `error` are breaches the keeper is retrying.
- **Logs.** `railway logs --service <name>`. Services log `service iteration failed; retrying` on a failed loop iteration and never log secret values.
- **Uptime check** ([issue #23](https://github.com/ddboy19912/bonded/issues/23)). UptimeRobot calls `GET /health` on the public API every 5 minutes and emails the founder when it fails (Telegram alerts are a paid UptimeRobot feature). Setup below.
- **Alerts** ([issue #24](https://github.com/ddboy19912/bonded/issues/24)). The services post problems to a Telegram chat. Setup and thresholds below.

### Alerts

The `api`, `keeper` and `arena-worker` services send operations alerts to one Telegram chat through a bot, using the Bot API. Alerts are off unless both `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` are set on a service. The code is `apps/api/src/alerts.ts`.

| Alert                                                             | Sent by                        | When                                                                                                                                                                           |
| ----------------------------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Started                                                           | every service with the secrets | Once per start. A deploy or restart announces itself, which doubles as each service's test alert                                                                               |
| Crashed                                                           | every service with the secrets | An error would end the process. It alerts (waiting at most 5 seconds), then exits so Railway restarts it                                                                       |
| A loop keeps failing                                              | every service with the secrets | 3 failed iterations in a row of a service loop (EVM or Solana keeper, TEE checks, rating or bounty worker, event retention, the watchdog). Another message when it works again |
| Keeper out of gas                                                 | keeper                         | The keeper's own wallet holds less than 0.002 ETH. Without gas every claim and premium accrual fails and retries                                                               |
| Keeper lag                                                        | keeper                         | The keeper's scanned block is more than 10 minutes and more than 100 blocks behind the chain head. Both must hold, so a quiet chain doesn't alert                              |
| Stuck claims                                                      | keeper                         | A breach has stayed `pending` with an error for 10 minutes (measured from when the keeper process first saw it failing, so a restart delays the alert rather than losing it)   |
| Failed rating, premium accrual, Solana claim or bounty validation | keeper                         | A `rating.failed`, `keeper.accrual_failed`, `solana.claim.failed` or `bounty.failed` event. Events from before the keeper started are not replayed                             |

The keeper's checks run once a minute. Limits: the same alert is sent at most once every 30 minutes, and each service sends at most 20 messages an hour. Messages are built from fixed text and ids only: never error messages (which can carry the RPC URL and its key), secrets or attack payloads.

Setup (founder action items 13 and 14 in `docs/PLAN.md`):

1. Create a bot with @BotFather in Telegram and copy its token. Send the bot one message from the chat that should receive alerts.
2. Find the chat id, with the token only in your shell. The script prints chat ids and names, never the token:

```bash
TELEGRAM_BOT_TOKEN=<token> node apps/api/scripts/telegram-chat-id.mjs
```

3. Set both secrets on `api` and `keeper` (and on `arena-worker`, optionally, for its crash and loop alerts; the keeper already reports failed ratings). Each command reads the value from stdin, so it stays out of shell history:

```bash
railway variables --service keeper --set-from-stdin TELEGRAM_BOT_TOKEN
```

```bash
railway variables --service keeper --set TELEGRAM_CHAT_ID=<chat id>
```

`.railway/railway.ts` lists both on `api` and `keeper` with `preserve()`, so an apply keeps their values. To give `arena-worker` its own alerts, add the same two lines to it there too.

4. Setting a variable redeploys the service, so each one posts "Started". To see one sample of every alert, marked TEST:

```bash
railway ssh --service keeper -- node apps/api/scripts/test-alerts.mjs
```

### Uptime check

UptimeRobot (free plan) watches the public API from outside Railway, so it also catches a Railway outage, which the services can't report themselves.

1. Add a monitor: type HTTP(s), URL `https://api-production-ba50.up.railway.app/health`, interval 5 minutes.
2. In the monitor's **Integrations & team**, keep the account's email contact ticked. Email alerts are free; Telegram needs a paid plan, so the services' own Telegram alerts (above) cover the chat.
3. `/health` answers 200 with `{"ok":true,"chainId":46630}` when the API and its database are up, and 503 otherwise.
