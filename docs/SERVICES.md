# Day 7 services

Run `pnpm test:services` for real Postgres and Anvil integration tests without Docker. Install Node 22+, pnpm 10.33.0 and Foundry first. `pnpm install` allows the embedded Postgres native setup script through the workspace allowlist.

For long-running services, set `DATABASE_URL`, `RPC_URL`, `DEPLOYMENT_FILE`, `ATTESTER_KEY`, `KEEPER_KEY` and `API_TOKEN` in `.env`. The API token must have at least 24 characters. Use separate attester and keeper accounts across deployed processes to avoid nonce contention. Both need testnet gas; only the attester must be registered with the registry. `ROLE` is `api`, `keeper`, `arena-worker` or `all`. Run `pnpm services`. Migrations run under a database lock before each role starts. `ROLE=migrate node apps/api/dist/main.js` runs migrations alone after building.

`docker compose up --build` runs Postgres 16 and all roles. Docker must be running and the configured RPC must be reachable inside the container. The image does not depend on git submodules being present: the Dockerfile fetches forge-std and OpenZeppelin at the commits the repository pins unless the copied checkout is readable and already at those commits. This covers Railway's source snapshot, which has no submodules, and local builds, where `.dockerignore` drops the git metadata. If you update a submodule, update `FORGE_STD_COMMIT` or `OPENZEPPELIN_COMMIT` in the Dockerfile to match `git ls-tree HEAD contracts/evm/lib/forge-std contracts/evm/lib/openzeppelin-contracts`.

## Railway

The Railway project (Postgres, its volume, and the `api`, `keeper`, `arena-worker` and `sentinel` services) is defined in `.railway/railway.ts`: the Dockerfile build, start command, health check and non-secret variables. Restart on failure (10 retries) and sleeping off are Railway's defaults, so the file leaves them out; spelling them out makes every plan report a false change. Signing keys and the API token are secrets kept on Railway; the file marks them `preserve()` so their values never enter the repository. The public domain is generated by Railway and is not in the file.

To change the setup, edit that file, then run the following from the repository root with the Railway CLI linked to the project:

```bash
railway config plan
```

`plan` changes nothing and lists what would change. Review it, especially anything it would destroy: a resource removed from the file is deleted on apply. Then run `railway config apply`. There is no automatic apply on merge while CI is paused, so apply after the change is merged to `main`.

Setting a secret (for example a new `KEEPER_KEY`) is done on Railway, not in the file:

```bash
grep '^KEEPER_KEY=' .env | cut -d= -f2- | tr -d '\n' | railway variables --service keeper --set-from-stdin KEEPER_KEY
```

### Sentinel

The `sentinel` service is different: it builds `services/sentinel/Dockerfile` (Laya's Python server, see `services/sentinel/README.md`), listens only on the private network at `http://sentinel.railway.internal:8000`, and has a 4 GB memory cap and 2 vCPUs. It pins the model with `SENTINEL_MODEL_REVISION`; change that only after the held-out evaluation (`docs/SENTINEL.md`). Its two secrets are set once:

- `HF_TOKEN`: a Hugging Face **read** token (huggingface.co → Settings → Access Tokens → type Read), so it can download the private model. Not the write token used on Kaggle.
- `LAYA_API_KEY`: the bearer key callers send. Generate one; callers read the same value.

The first command waits silently: paste the read token and press Enter. It isn't echoed or stored in shell history.

```bash
read -rs HF && printf %s "$HF" | railway variables --service sentinel --set-from-stdin HF_TOKEN; unset HF
```

```bash
openssl rand -hex 32 | tr -d '\n' | railway variables --service sentinel --set-from-stdin LAYA_API_KEY
```

The first start downloads the model (about 1.7 GB), so the deploy takes a few minutes before its health check passes.

Do not accept Railway's offer to create one service per pnpm package (`@bonded/arena`, `@bonded/api` and so on). The packages are not separate services; all three services build the root `Dockerfile` and differ only in `ROLE`.

Railway injects `PORT`; the API reads it. Every service runs migrations under a database lock before starting, so start order does not matter.

The hosted services load `config/agents.46630.json` (agent 2, the scripted hardened adapter from Gate 1; its mandate hash matches the one attested on chain). Provision agents through `AGENTS_FILE`, a JSON array of `{ "kind": "hardened", "mandate": <full EVM mandate>, "codeHash": "0x…" }` records. `kind` is `hardened` or `vulnerable`, selecting the existing scripted demo adapter. Agent IDs must already exist on the configured chain; the mandate's chain and agent ID must match. Keep this file server-owned. On startup, a supplied file is the complete configured set for that chain: removed agents are disabled and their queued/running jobs are failed (active workers stop at their next lease check), while historical reports and attestations remain readable. An empty array disables the entire chain's configured set; omitting `AGENTS_FILE` leaves it unchanged. Already-broadcast transactions cannot be cancelled. Arbitrary submitted agent code and LLM configurations are outside this initial worker interface.

POST endpoints require `Authorization: Bearer <API_TOKEN>`. GET endpoints are public.

Browsers can call the API only from origins listed in `WEB_ORIGINS` (comma-separated, for example `http://localhost:5173,https://bonded.vercel.app`). Other origins get no CORS headers. The hosted `api` service sets it in `.railway/railway.ts`.

| Request | Body / result |
|---|---|
| `GET /health` | Database availability and configured chain ID |
| `POST /arena/runs` | `{ "agentId": "1" }` → `runId` |
| `GET /arena/runs/:id` | Status, report and retry error |
| `GET /arena/runs/:id/report` | Report or 202 while pending |
| `GET /agents/:id/score` | Latest worker-posted signed attestation and transaction hash |
| `POST /quotes` | `{ "agentId": "1", "vault": "0x…", "coverAmount": "20000000000" }` → signed quote |
| `GET /events?runId=<uuid>` | SSE episode feed; optional run filter, `Last-Event-ID` replay |

Amounts are integer strings in base-asset units. Quotes use the registry score and one block's pool exposure, bond and caps, then simulate `buyCover` as the guardian. Quotes do not reserve capacity: chain state can change before purchase, and the contract checks again. Missing or invalid chain state currently returns a generic 503; underwriting cap failures return 409.

The report endpoint returns the exact JSON bytes hashed by the attestation; a text column preserves them alongside the queryable JSONB report. Migration 2 adds this column without fabricating original bytes for older rows.

The worker rates on a local fork, never against the live RPC. It awaits every episode write, saves the report and signature, then posts the attestation to the configured registry. Jobs get at most three attempts, including expired leases from process crashes, and then remain `failed` for inspection. The next claim reaps exhausted leases, updates rating status and emits a failure event. The keeper role deletes `events` rows older than `EVENTS_RETENTION_DAYS` (default 30) once an hour, in batches of 10,000, oldest first. Ratings, reports, attestations and claims are not touched. An SSE client resuming from a deleted `Last-Event-ID` continues from the oldest kept event. SSE admits at most five simultaneous subscribers per API instance, returning 503 beyond the limit. Each stream reuses its reserved listener for replay queries, leaving the rest of the 15-connection pool for ordinary operations. Connection waits and stream queries time out after five seconds. Shutdown stops admission, aborts active streams (including slow readers), waits for listener cleanup, and then closes Postgres.

The keeper scans up to 500 blocks per tick, with five confirmations by default (`KEEPER_CONFIRMATIONS=0` only for local tests). It accrues active policies every minute. Breaches stay pending after RPC or liquidity failures. No-match breaches become `ignored` with a reason once the policy cursor has passed the breach timestamp; until then they remain pending so a not-yet-indexed policy at the same timestamp is not missed. Claims are checked against historical coverage windows and simulated after accrual. A deep reorg triggers an error and stops scanning until an operator reconciles the database. Monitor service error logs and pending jobs; there is no alerting integration yet.

## Monitoring

What watches the hosted services today:

- **Health check.** Railway calls `GET /health` on `api` during each deploy and keeps the previous deployment serving if the new one fails it. The endpoint reports database availability and the configured chain ID.
- **Restarts.** All three services restart on failure, up to 10 times. A service that keeps crashing stops and shows as crashed in the dashboard; Railway emails the workspace owner about failed deploys and crashes.
- **Spending.** The workspace has a $10 soft limit (email) and a $25 hard limit (Railway stops the services). Normal use is about $3 a month: roughly 0.2 GB of memory and 0.03 vCPU across the four services. Check with `railway usage`.
- **Keeper progress.** `keeper_cursors.block_number` should stay within a few blocks of the chain head. `handled_events` rows with `status='pending'` and a non-empty `error` are breaches the keeper is retrying.
- **Logs.** `railway logs --service <name>`. Services log `service iteration failed; retrying` on a failed loop iteration and never log secret values.

Not yet in place: an external uptime check on the public `/health` URL, and alerts to a chat channel. These are tracked as [issue #23](https://github.com/ddboy19912/bonded/issues/23) and [issue #24](https://github.com/ddboy19912/bonded/issues/24), and in the Deferred work table in `docs/PLAN.md`.
